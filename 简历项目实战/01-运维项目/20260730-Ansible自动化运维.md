# Ansible 自动化运维 — 百台服务器批量管理

## 📄 简历写法（可直接抄）

> **服务器自动化运维体系** · 项目角色：独立实施 · 2026.XX
>
> - 针对多机环境**重复手工操作**（初始化、补丁、巡检）耗时且不一致的问题，编写 **Ansible Playbook** 实现标准化批量管理
> - 新机器初始化从 **2 小时/台** 降至 **3 分钟/台**且零遗漏；批量安全补丁执行从 **3 天** 缩短到 **30 分钟**
> - 编写**自动巡检 Playbook**，每日定时执行并生成 HTML 报告，隐患发现率提升 **50%**

> [!tip] 旁批：个人怎么练"百台"
> 不用真有一百台——开 2~3 台云服务器（或用 Multipass/Docker 在本机起多个容器当"主机"）即可完整练习所有概念。面试时讲"设计目标是支持百台规模" + 展示 playbook 的分批执行（serial）、并发（forks）设计，一样证明能力。

## 🧰 技术栈

| 工具 | 用途 | 为什么选它 |
|------|------|------------|
| Ansible | 自动化引擎 | **无 agent**（SSH 直连）是最核心的选型理由——不用在 100 台机器上先装客户端 |
| YAML Playbook | 任务定义 | 声明式、可读性强、可进 Git 版本管理 |
| Ansible Galaxy | 复用社区角色 | nginx、docker 等常见角色不用从零写 |
| Cron / AWX | 定时执行 | AWX 是 Ansible 的开源 Web 管理界面（可选进阶） |

## 🛠️ 详细操作步骤

### 步骤 1：控制机安装与免密配置

```bash
# 控制机（你的电脑或一台管理机）安装
pip install ansible
ansible --version

# 生成 SSH 密钥并分发到所有被管机器
ssh-keygen -t ed25519
ssh-copy-id user@192.168.1.10
ssh-copy-id user@192.168.1.11
ssh-copy-id user@192.168.1.12
```

### 步骤 2：编写主机清单（Inventory）

```ini
# inventory/hosts.ini
[web]
192.168.1.10
192.168.1.11

[db]
192.168.1.12

[all:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/id_ed25519
```

```bash
# 验证连通性——Ansible 的"Hello World"
ansible all -i inventory/hosts.ini -m ping
# 192.168.1.10 | SUCCESS => { "ping": "pong" } ...
```

> [!tip] 旁批：分组是批量管理的核心思想
> web/db 分组后，可以只对 web 组推应用、只对 db 组做备份策略。进阶还能用动态 inventory 从云平台 API 自动拉取主机列表——公司机器经常上下线，静态文件维护不过来。

### 步骤 3：第一个实战 Playbook — 新机器初始化

```yaml
# playbooks/init-server.yml
- name: 新服务器标准化初始化
  hosts: all
  become: yes                    # sudo 执行
  vars:
    timezone: Asia/Shanghai
    ssh_port: 22222

  tasks:
    - name: 更新软件源缓存
      apt:
        update_cache: yes

    - name: 安装基础工具
      apt:
        name:
          - vim
          - htop
          - curl
          - net-tools
          - fail2ban              # SSH 防爆破，安全基线
        state: present

    - name: 设置时区
      timezone:
        name: "{{ timezone }}"

    - name: 修改 SSH 端口（安全加固）
      lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^#?Port '
        line: "Port {{ ssh_port }}"
      notify: 重启sshd

    - name: 禁用密码登录，仅密钥
      lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^#?PasswordAuthentication '
        line: "PasswordAuthentication no"
      notify: 重启sshd

    - name: 创建运维账号并授权
      user:
        name: ops
        groups: sudo
        shell: /bin/bash

  handlers:
    - name: 重启sshd
      service:
        name: sshd
        state: restarted
```

```bash
# 执行：-C 先 dry-run 预览，确认无误后真跑
ansible-playbook -i inventory/hosts.ini playbooks/init-server.yml -C
ansible-playbook -i inventory/hosts.ini playbooks/init-server.yml
```

> [!important] 旁批：幂等性 — Ansible 最重要的概念（面试必考）
> 同一个 playbook 跑 100 遍，结果和跑 1 遍一样：装过的包跳过、改过的配置不重复改。这是 `apt`/`lineinfile` 等**模块**的功劳——它们检查当前状态再决定是否动作。
> **反例**：自己写 `shell: echo "Port 22" >> sshd_config`，每跑一遍多一行，机器就废了。能用模块就不用 shell/command。

### 步骤 4：批量安装 Docker + node_exporter（和监控项目联动）

```yaml
# playbooks/setup-monitor-agent.yml
- name: 批量部署 Docker 与监控 agent
  hosts: all
  become: yes
  tasks:
    - name: 安装 Docker
      apt:
        name: docker.io
        state: present

    - name: 启动 Docker 服务
      service:
        name: docker
        state: started
        enabled: yes

    - name: 部署 node_exporter 容器
      docker_container:
        name: node-exporter
        image: prom/node-exporter:latest
        restart_policy: always
        ports:
          - "9100:9100"
        volumes:
          - /proc:/host/proc:ro
          - /sys:/host/sys:ro
        command:
          - --path.procfs=/host/proc
          - --path.sysfs=/host/sys
```

### 步骤 5：自动巡检 Playbook（体现"主动运维"思维）

```yaml
# playbooks/daily-inspect.yml
- name: 每日巡检并生成报告
  hosts: all
  gather_facts: yes
  tasks:
    - name: 采集磁盘使用率
      shell: df -h / | awk 'NR==2 {print $5}'
      register: disk_usage
      changed_when: false

    - name: 采集内存使用率
      shell: free | awk '/Mem:/ {printf "%.0f", $3/$2*100}'
      register: mem_usage
      changed_when: false

    - name: 采集最近登录失败次数
      shell: grep "Failed password" /var/log/auth.log 2>/dev/null | wc -l
      register: failed_logins
      changed_when: false
      ignore_errors: yes

    - name: 汇总到控制机生成报告
      template:
        src: templates/report-row.j2
        dest: "./reports/{{ inventory_hostname }}.txt"
      delegate_to: localhost       # 关键：在控制机本地生成
```

```bash
# 挂 cron 每天 9 点自动跑
0 9 * * * cd /opt/ansible && ansible-playbook -i inventory/hosts.ini playbooks/daily-inspect.yml
```

> [!tip] 旁批：changed_when: false 是什么
> shell 模块默认每次都报 "changed"（它不知道你的命令改没改东西），巡检这种只读操作要显式声明 `changed_when: false`，否则 playbook 统计全是黄色 changed，看不出真正的问题。

### 步骤 6：控制执行节奏（百台规模的精髓）

```yaml
- name: 分批滚动更新
  hosts: web
  serial: "30%"            # 每批只动 30% 的机器，出问题立刻停
  max_fail_percentage: 10  # 超过 10% 失败就整体中止
  tasks:
    - name: 更新应用
      # ...
```

> [!tip] 旁批：serial 是血泪经验
> 一次推全部 100 台，配置写错就是 100 台同时挂 = 重大事故。`serial: 30%` 让更新像 K8s 滚动发布一样分批走，第一批有问题 Ctrl+C 还来得及。面试讲出这个，说明你有**变更风险意识**——这是初级和中级运维的分水岭。

## 📊 成果量化模板

| 指标 | 手工时代 | Ansible 后 |
|------|----------|------------|
| 新机初始化 | 2 小时/台，靠文档 + 记忆 | 3 分钟/台，playbook 即文档 |
| 批量补丁 | 3 天（逐台登录） | 30 分钟（一键执行） |
| 环境一致性 | 各机器配置漂移严重 | 幂等执行，配置统一 |
| 巡检 | 想做但没时间 | 每日自动 + 报告 |

## ❓ 面试高频问题

1. **Ansible 和 Shell 脚本批发的本质区别？** → 幂等性、模块化、声明式、可读性、可版本管理；Shell 脚本是"怎么做"，Playbook 是"要什么状态"
2. **Ansible 和 SaltStack/Puppet 比呢？** → Ansible 无 agent（SSH），上手最快；SaltStack 有 agent 但性能强、事件驱动；公司存量用什么就兼容什么，思路相通
3. **Playbook 里密钥怎么管？** → ansible-vault 加密敏感变量文件，`--ask-vault-pass` 执行时解密
4. **Ansible 适合做什么、不适合什么？** → 适合：配置管理、批量变更、部署编排；不适合：实时监控（那是 Prometheus 的活）、长时间状态维持（那是 K8s 的活）
