# CI/CD 流水线搭建 — 部署从 2 小时到 10 分钟

## 📄 简历写法（可直接抄）

> **CI/CD 自动化部署平台** · 项目角色：主导搭建 · 2026.XX
>
> - 针对手动部署平均耗时 **2 小时**、人为失误率高的问题，基于 **GitLab CI + Docker** 设计并实现覆盖「构建→测试→部署→通知」的全自动流水线
> - 单次发布耗时降至 **10 分钟**，发布频率从每周 1 次提升至每日多次，部署事故率下降 **80%**
> - 引入**镜像版本管理 + 一键回滚**机制，回滚操作从 30 分钟缩短到 **1 分钟内**

> [!tip] 旁批：数字怎么来
> 没有公司数据就按个人项目如实写："个人博客/开源项目 CI/CD 改造"。面试官追问时，讲清楚**改造前后的对比逻辑**（手动部署有哪些步骤、每步多久、哪步易错）比编数字更有说服力。

## 🧰 技术栈

| 工具 | 用途 | 为什么选它（面试考点） |
|------|------|------------------------|
| GitLab CE / Gitee Go | 代码托管 + CI 引擎 | 国内网络可达，自带 CI 免维护 Jenkins |
| GitLab Runner | 执行流水线任务的 agent | 支持 Docker executor，环境隔离干净 |
| Docker | 应用容器化打包 | 环境一致性，"一次构建到处运行" |
| Docker Compose | 目标机编排 | 单机场景比 K8s 轻量，学习成本低 |
| Nginx | 反向代理 + 静态资源 | 标配，支持蓝绿切换 |
| 钉钉/企微 Webhook | 部署结果通知 | 免费，团队可见 |

## 🛠️ 详细操作步骤

### 步骤 0：准备环境

```bash
# 一台 2C4G 云服务器（Ubuntu 22.04）
# 安装 Docker
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker

# 安装 Docker Compose
sudo apt install docker-compose-plugin -y
docker compose version
```

### 步骤 1：部署 GitLab（或用 Gitee 免费版替代）

```bash
# Docker 一键起 GitLab CE（4G 内存刚好够）
docker run -d --name gitlab \
  -p 8929:8929 -p 2224:22 \
  -v /srv/gitlab/config:/etc/gitlab \
  -v /srv/gitlab/logs:/var/log/gitlab \
  -v /srv/gitlab/data:/var/opt/gitlab \
  gitlab/gitlab-ce:latest
```

> [!tip] 旁批：内存不够的替代方案
> GitLab 很吃内存（空载 ~2.5G）。服务器只有 2G 的话直接用 **Gitee Go**（码云自带流水线，免费 200 分钟/月构建时长），pipeline 语法和 GitLab CI 几乎一样，简历上写哪个都行。

### 步骤 2：注册 GitLab Runner

```bash
# 安装 Runner（Docker 方式）
docker run -d --name gitlab-runner --restart always \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest

# 注册到 GitLab（token 在 GitLab → Settings → CI/CD → Runners 获取）
docker exec -it gitlab-runner gitlab-runner register \
  --url http://你的IP:8929 \
  --token <REGISTRATION_TOKEN> \
  --executor docker \
  --docker-image docker:24
```

> [!warning] 旁批：为什么挂载 docker.sock
> Runner 用 Docker executor 跑任务时，构建镜像需要访问宿主机 Docker。挂 sock 是最简单的方式（叫 Docker-out-of-Docker）。面试可能追问安全性——答案：生产环境可用 `kaniko` 无特权构建替代。

### 步骤 3：编写 `.gitlab-ci.yml`（项目核心）

在应用仓库根目录创建：

```yaml
stages:
  - test
  - build
  - deploy

variables:
  IMAGE_NAME: registry.example.com/myapp
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA        # 用 commit 短哈希做版本号

# ---- 阶段1：测试 ----
unit-test:
  stage: test
  image: python:3.11
  script:
    - pip install -r requirements.txt
    - pytest tests/ -v --junitxml=report.xml
  artifacts:
    reports:
      junit: report.xml                  # 测试结果在 GitLab UI 展示

# ---- 阶段2：构建镜像并推送 ----
build-image:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker login -u $REGISTRY_USER -p $REGISTRY_PASS registry.example.com
    - docker build -t $IMAGE_NAME:$IMAGE_TAG -t $IMAGE_NAME:latest .
    - docker push $IMAGE_NAME:$IMAGE_TAG
    - docker push $IMAGE_NAME:latest
  only:
    - main                               # 只有 main 分支才构建

# ---- 阶段3：部署到生产服务器 ----
deploy-prod:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | tr -d '\r' | ssh-add -
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh
    - ssh-keyscan -H $PROD_HOST >> ~/.ssh/known_hosts
  script:
    - ssh $PROD_USER@$PROD_HOST "
        cd /opt/myapp &&
        docker compose pull &&
        docker compose up -d &&
        docker image prune -f"
  after_script:
    - 'curl -H "Content-Type: application/json" -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"✅ myapp 部署完成: $IMAGE_TAG\"}}" $DINGTALK_WEBHOOK'
  when: manual                           # 手动触发，生产环境保险
```

> [!tip] 旁批：三个关键设计决策（面试必问）
> 1. **IMAGE_TAG 用 commit 哈希而非 latest**：每个镜像可追溯、可回滚——用 latest 你永远不知道线上跑的是哪个版本
> 2. **deploy 设 `when: manual`**：自动到 build 为止，生产部署留一个人工确认按钮，这是公司里的标准做法
> 3. **密钥全走 CI Variables**（Settings → CI/CD → Variables），永不写进仓库——SSH_PRIVATE_KEY、REGISTRY_PASS 都设成 masked 变量

### 步骤 4：编写应用 Dockerfile（多阶段构建）

```dockerfile
# ---- 构建阶段 ----
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# ---- 运行阶段 ----
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

> [!tip] 旁批：为什么多阶段构建
> 构建工具（gcc、pip 缓存）不进最终镜像，镜像体积从 ~1.1GB 降到 ~200MB。镜像越小：推送越快、部署越快、攻击面越小。面试说得出这三个理由就过关。

### 步骤 5：目标服务器 compose 配置

```yaml
# /opt/myapp/docker-compose.yml
services:
  app:
    image: registry.example.com/myapp:latest
    restart: always
    ports:
      - "8000:8000"
    environment:
      - ENV=production
  nginx:
    image: nginx:alpine
    restart: always
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf
```

### 步骤 6：验证回滚（面试加分项）

```bash
# 出问题时，在目标机执行——直接改镜像 tag 回上一版
cd /opt/myapp
sed -i 's/myapp:latest/myapp:abc1234/' docker-compose.yml
docker compose up -d
# 全程 < 1 分钟
```

## ❓ 面试高频问题

1. **流水线里怎么做测试？** → test 阶段跑 pytest，失败则流水线中断，后续阶段不执行；测试报告用 artifacts 上传展示
2. **怎么保证密钥安全？** → CI Variables（masked）+ 权限分级，密钥不进仓库、不进镜像、不进日志
3. **蓝绿部署和滚动更新区别？** → 蓝绿：两套环境瞬时切换，回滚快但资源翻倍；滚动：分批替换，省资源但发布过程中新旧版本并存
4. **CI 和 CD 的边界在哪？** → CI 到"构建出可部署的产物（镜像）"为止；CD 是"把产物安全地放到生产"
