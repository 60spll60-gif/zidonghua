# K8s 容器编排实战 — 零停机滚动发布

## 📄 简历写法（可直接抄）

> **微服务容器化与 K8s 编排改造** · 项目角色：方案设计 + 实施 · 2026.XX
>
> - 将 **N 个微服务**从单机 Docker Compose 迁移至 **Kubernetes 集群**，实现服务自动调度、故障自愈与弹性扩缩容
> - 通过 **Deployment 滚动更新 + Readiness 探针**实现发布全程**零停机**，用户无感知
> - 配置 **HPA 水平自动扩缩容**（基于 CPU/内存），高峰期自动从 2 副本扩到 8 副本，资源成本较固定高配方案下降 **35%**

> [!tip] 旁批：个人没有微服务系统怎么办
> 用开源项目练手即可：`microservices-demo`（Google 出品，11 个微服务的在线商店）或 `mall`（国产电商系统）。部署别人的系统同样能覆盖 K8s 全部核心技能点，简历写"基于开源微服务系统完成 K8s 部署改造与调优"。

## 🧰 技术栈

| 工具 | 用途 | 为什么选它 |
|------|------|------------|
| k3s / kubeadm | 搭 K8s 集群 | k3s 单机 1 条命令起集群，个人练习神器；kubeadm 是生产标准 |
| Kubernetes | 容器编排 | 云原生事实标准 |
| Helm | 应用打包部署 | K8s 的"应用商店"，复杂应用一键装 |
| Ingress-Nginx | 统一入口/域名路由 | 替代每个服务一个 NodePort 的混乱 |
| Metrics Server | 资源指标采集 | HPA 扩缩容的数据来源 |

## 🛠️ 详细操作步骤

### 步骤 1：一条命令起 k3s 集群

```bash
# 在服务器上执行（1~2 分钟完成）
curl -sfL https://get.k3s.io | sh -

# 验证
sudo k3s kubectl get nodes
# NAME    STATUS   ROLES                  AGE   VERSION
# node1   Ready    control-plane,master   1m    v1.29.x

# 把 kubeconfig 配好，之后直接用 kubectl
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $USER ~/.kube/config
```

> [!tip] 旁批：k3s vs kubeadm vs minikube 怎么选
> - **minikube**：跑在自己电脑虚拟机里，适合纯学习，但"不像生产"
> - **k3s**：轻量发行版（<100MB），单台 2C4G 云服务器就能跑，体验和真实集群 99% 一致 —— **个人实操首选**
> - **kubeadm**：生产标准部署方式，面试时聊"我用 kubeadm 搭过 3 节点集群"是加分项，时间充裕再练

### 步骤 2：部署应用 — 三个核心对象

```yaml
# app.yaml —— Deployment + Service + Ingress 三件套
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
spec:
  replicas: 3                          # 3 副本，挂 1 个还剩 2 个
  strategy:
    rollingUpdate:
      maxSurge: 1                      # 更新时最多多 1 个
      maxUnavailable: 0                # 更新时最少可用 0 个 = 零停机关键
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      containers:
      - name: webapp
        image: registry.example.com/myapp:v1.2.0
        ports:
        - containerPort: 8000
        resources:
          requests:                    # 调度依据：保证有 100m CPU
            cpu: 100m
            memory: 128Mi
          limits:                      # 防爆：最多用 500m
            cpu: 500m
            memory: 512Mi
        readinessProbe:                # 就绪探针：没 ready 不接流量
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:                 # 存活探针：假死自动重启
          httpGet:
            path: /health
            port: 8000
          initialDelaySeconds: 15
          periodSeconds: 20
---
apiVersion: v1
kind: Service
metadata:
  name: webapp-svc
spec:
  selector:
    app: webapp
  ports:
  - port: 80
    targetPort: 8000
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: webapp-ingress
spec:
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: webapp-svc
            port:
              number: 80
```

```bash
kubectl apply -f app.yaml
kubectl get pods -w        # 观察 3 个 Pod 逐个 Running
```

> [!important] 旁批：零停机的两个支柱（面试必考）
> 1. **`maxUnavailable: 0`** — 更新过程中可用副本数永远 ≥ 期望值，先拉起新版本、就绪后才杀旧版本
> 2. **Readiness 探针** — 新 Pod 必须通过了 `/health` 检查才被加进 Service 的负载池接流量。没有它，应用启动慢的几秒内流量会打到还没准备好的 Pod 上 = 请求失败
>
> 只改镜像不加探针 ≠ 零停机，很多人实操栽在这里。

### 步骤 3：发布新版本（体验滚动更新）

```bash
# 改镜像版本 = 触发滚动更新
kubectl set image deployment/webapp webapp=registry.example.com/myapp:v1.3.0

# 实时观察：新 Pod 逐个创建→就绪→旧 Pod 逐个删除
kubectl rollout status deployment/webapp

# 出问题？一条命令回滚到上一版
kubectl rollout undo deployment/webapp

# 查看历史版本
kubectl rollout history deployment/webapp
```

### 步骤 4：配置 HPA 自动扩缩容

```bash
# 先装 metrics-server（k3s 自带，kubeadm 集群需要单独装）
kubectl top nodes        # 验证能拿到指标

# 创建 HPA：CPU 超过 50% 就扩容，2~8 副本之间伸缩
kubectl autoscale deployment webapp \
  --cpu-percent=50 --min=2 --max=8
```

> [!tip] 旁批：扩缩容阈值怎么定
> CPU 50% 是常用起点。定太高（如 90%）：等触发扩容时服务已经卡了；定太低（如 20%）：稍微抖动就扩容，浪费钱。面试可以补一句："生产环境更精细的做法是基于 QPS/延迟的自定义指标（KEDA）"。

### 步骤 5：压测验证弹性（最有成就感的环节）

```bash
# 起一个压测 Pod 狂打流量
kubectl run -i --tty loadgen --image=busybox --restart=Never -- /bin/sh
# 容器内执行：
while true; do wget -q -O- http://webapp-svc/; done

# 另开终端观察：CPU 飙升 → HPA 触发 → 副本数 2→4→8
kubectl get hpa -w
kubectl get pods -w
```

### 步骤 6：HTTPS 证书（可选加分）

```bash
# Helm 装 cert-manager，自动签发 Let's Encrypt 证书
helm repo add jetstack https://charts.jetstack.io
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --set installCRDs=true
```

## 📊 成果量化模板

| 指标 | 改造前（Compose） | 改造后（K8s） |
|------|-------------------|---------------|
| 发布停机时间 | 每次 5~10 分钟 | 0 秒 |
| 故障恢复 | 人工发现+重启，~30 分钟 | 自愈，~30 秒 |
| 高峰应对 | 固定 8 台常开 | 2~8 弹性伸缩，省 35% 成本 |
| 扩容操作 | 手动加机器部署，小时级 | 自动，分钟级 |

## ❓ 面试高频问题

1. **Pod 挂了就数据丢了怎么办？** → 无状态应用无所谓；有状态（数据库）用 StatefulSet + PV/PVC 持久卷，数据库一般不放进 K8s 或用 Operator 管理
2. **Service 是怎么找到 Pod 的？** → 通过 label selector，Service 维护 endpoints 列表，kube-proxy 负责转发（iptables/ipvs 模式）
3. **Deployment 和 StatefulSet 区别？** → Deployment 面向无状态，Pod  interchangeable；StatefulSet 有稳定网络标识和存储，面向有状态应用
4. **K8s 集群里 DNS 怎么工作？** → CoreDNS 提供集群内服务发现，`服务名.命名空间.svc.cluster.local`
5. **node 挂了 Pod 怎么办？** → 控制器发现 Pod 失联，自动在健康节点重建（自愈）
