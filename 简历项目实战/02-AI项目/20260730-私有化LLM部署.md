# 私有化 LLM 部署 — 数据不出内网的合规方案

## 📄 简历写法（可直接抄）

> **大模型私有化推理平台建设** · 项目角色：独立完成 · 2026.XX
>
> - 针对业务数据**禁止出内网**的合规要求，基于 **vLLM + 开源大模型（Qwen2.5/DeepSeek-R1）** 搭建私有化推理服务
> - 通过 **量化（AWQ/GPTQ）+ 连续批处理（Continuous Batching）** 优化，单卡 RTX 4090 支撑 **20+ 并发**，首 token 延迟 < 1s
> - 提供 **OpenAI 兼容 API**，上层应用零改造切换；配套 Prometheus 监控 QPS/延迟/GPU 利用率

> [!tip] 旁批：这个项目为什么"值钱"
> 金融、政务、医疗行业**必须**私有化部署（数据合规是红线），但会部署 + 调优 + 监控大模型服务的人远少于会调 API 的人。这是 AI 岗和运维岗的**交叉稀缺技能**——运维背景的人做这个项目，比纯算法背景的人更有优势（服务化、监控、高可用是你的主场）。

## 🧰 技术栈

| 工具 | 用途 | 为什么选它 |
|------|------|------------|
| vLLM | 高性能推理引擎 | PagedAttention 显存管理 + 连续批处理，吞吐比原生高 **5~10 倍** |
| Ollama | 轻量本地部署 | 一条命令跑模型，开发调试神器，不适合高并发生产 |
| Qwen2.5-7B/14B | 开源基座模型 | 中文最强开源模型之一，Apache 2.0 可商用 |
| DeepSeek-R1-Distill | 推理模型 | 蒸馏版 7B/14B 可单卡跑，推理能力强 |
| Open WebUI | 开箱即用对话界面 | 类 ChatGPT 界面，接 Ollama/OpenAI 兼容 API |
| GPU（RTX 4090/A6000） | 推理硬件 | 4090 24G 是性价比之王；无卡可租 AutoDL（~¥1.5/时） |

## 🛠️ 详细操作步骤

### 步骤 0：摸清硬件账（先算再跑）

| 模型规模 | FP16 显存 | INT8 量化 | INT4 量化 | 可行的卡 |
|----------|-----------|-----------|-----------|----------|
| 7B | ~14GB | ~8GB | ~5GB | 4090(24G) 轻松，3060(12G) 量化可行 |
| 14B | ~28GB | ~15GB | ~9GB | 4090 需量化 |
| 32B | ~64GB | ~34GB | ~20GB | 4090 INT4 勉强，A6000(48G) 稳 |
| 70B | ~140GB | ~72GB | ~40GB | 双卡 A6000 / A100 |

> [!important] 旁批：显存估算公式（面试高频）
> **参数量 × 每参数字节数**。FP16 每参数 2 字节 → 7B × 2B = 14GB；INT4 量化每参数 0.5 字节 → 7B 只要 3.5GB（加上 KV Cache 和框架开销实际 ~5GB）。KV Cache 随并发数增长，这是并发上不去的根本原因——vLLM 的 PagedAttention 就是解决这个问题的。

### 步骤 1：Ollama 快速验证（5 分钟跑起来）

```bash
# 安装（Linux）
curl -fsSL https://ollama.com/install.sh | sh

# 拉模型并运行
ollama pull qwen2.5:7b
ollama run qwen2.5:7b "用一句话解释什么是 RAG"

# Ollama 自带 OpenAI 兼容接口
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen2.5:7b", "messages": [{"role":"user","content":"你好"}]}'
```

### 步骤 2：vLLM 生产级部署（核心）

```bash
# Docker 一条命令起 OpenAI 兼容服务
docker run -d --name vllm-server \
  --gpus all \
  -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.9 \
  --quantization awq                  # 量化省显存
```

```python
# 调用方式和 OpenAI API 完全一致——这就是"零改造切换"
from openai import OpenAI
client = OpenAI(base_url="http://服务器IP:8000/v1", api_key="EMPTY")
resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "写一个 Python 快排"}]
)
```

> [!tip] 旁批：三个关键启动参数
> - `--gpu-memory-utilization 0.9`：vLLM 预分配 90% 显存做 KV Cache 池，给小了并发上不去，给大了模型加载不了
> - `--max-model-len`：上下文窗口，设小一点（8192 vs 32768）KV Cache 池能容纳更多并发会话
> - `--quantization awq`：AWQ 是激活感知量化，比 naive INT4 掉点少；精度敏感场景换 `--quantization fp8`（4090 支持）

### 步骤 3：并发压测（量化成果的来源）

```bash
# 用 vLLM 官方 benchmark 工具
pip install vllm

python -m vllm.entrypoints.openai.benchmark_serving \
  --backend openai \
  --model Qwen/Qwen2.5-7B-Instruct \
  --host localhost --port 8000 \
  --num-prompts 200 \
  --request-rate 10

# 关注输出：
# Throughput: XX tokens/s     ← 总吞吐
# TTFT (Time To First Token)  ← 首 token 延迟，影响体感
# TPOT (Time Per Output Token)← 生成速度
```

### 步骤 4：挂 Open WebUI 提供对话界面

```bash
docker run -d --name open-webui \
  -p 3000:8080 \
  -e OPENAI_API_BASE_URL=http://host.docker.internal:8000/v1 \
  -e OPENAI_API_KEY=EMPTY \
  -v open-webui:/app/backend/data \
  ghcr.io/open-webui/open-webui:main

# 浏览器打开 http://服务器IP:3000 → 类 ChatGPT 界面，支持多用户/RAG/联网
```

### 步骤 5：Prometheus 监控推理服务（运维差异化优势）

vLLM 原生暴露 `/metrics` 端点，直接接入你监控项目里的 Prometheus：

```yaml
# prometheus.yml 增加一个 job
scrape_configs:
  - job_name: "vllm"
    static_configs:
      - targets: ["服务器IP:8000"]
    metrics_path: /metrics
```

可监控指标：`vllm:num_requests_running`（当前并发）、`vllm:gpu_cache_usage_perc`（KV Cache 占用率）、`vllm:time_to_first_token_seconds` 等。

> [!tip] 旁批：KV Cache 占用率是扩容量信号
> `gpu_cache_usage_perc` 长期 > 80% 说明并发快到顶了，新请求会排队——这时候该加卡或换量化方案。把这条做成 Grafana 告警，就是你简历上"AI 服务可观测性"的实证。

| 指标 | 数据 |
|------|------|
| 支撑并发 | 单卡 4090，20+ 并发会话 |

## ❓ 面试高频问题

1. **vLLM 为什么快？** → PagedAttention：像操作系统管理内存页一样管理 KV Cache，消除显存碎片；Continuous Batching：不等整批结束，完成一个插进一个，GPU 不空转
2. **量化损失多少精度？** → AWQ INT4 在多数任务上掉 1~3 个点，远小于显存收益；精度敏感场景用 FP8/INT8
3. **并发上不去怎么排查？** → 看 KV Cache 占用率（显存瓶颈）→ 降 max-model-len / 上量化 / 加卡；看 GPU util（计算瓶颈）→ 换更强卡或更小的模型
4. **Ollama 和 vLLM 怎么选？** → Ollama：个人开发、单机低并发、求简单；vLLM：生产、高并发、要监控和 SLA——讲出这个边界说明你理解"工具服务于场景"
5. **模型文件怎么管理？** → 公司场景一般从内网 HuggingFace 镜像站（hf-mirror）或对象存储拉取，配合版本目录管理，回滚 = 切版本目录
