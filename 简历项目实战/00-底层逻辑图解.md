# 8 个项目的底层逻辑 — 先懂"为什么"，再学"怎么做"

> [!tip] 怎么用这篇笔记
> 技术方案千千万，但每个项目背后都有一个**朴素的问题**和一个**朴素的解决思路**。先理解这一层，再看操作步骤时，每条命令你都知道它在解决什么。面试时也一样——面试官真正想听的就是这一层。

---

## 🖥️ 运维四件套：解决"机器多了人忙不过来"

运维的根本矛盾只有一句话：**服务器的数量和复杂度在涨，人的时间和精力不涨**。四个项目分别对付这个矛盾的一个侧面。

### 1. CI/CD 流水线 —— 把"人肉部署"变成"按一下按钮"

**朴素的问题**：手动部署 = 登录服务器 → 拉代码 → 装依赖 → 构建 → 重启服务 → 祈祷没漏步骤。做 10 次总会漏 1 次，漏的那次就是半夜的事故。

**底层逻辑**：部署是一串**固定顺序的步骤**，凡是固定步骤就该交给机器执行。流水线（Pipeline）的本质是"**把操作手册写成代码**"：
```
代码提交（触发）→ 机器按手册逐步执行 → 任何一步失败立即停下报警
```
> [!note] 关键认知
> 人做重复事会疲劳出错，机器不会。CI/CD 卖的不是"快"，是"**每次都一样**"——可重复性消灭了"在我电脑上明明是好的"这类问题。配套的两个安全设计：失败即停（测试不过就不许上线）、版本留痕（每个镜像对应一个 commit，出事能秒回滚）。

### 2. Kubernetes 容器编排 —— 给容器们请一个"全天候调度员"

**朴素的问题**：你有 20 个容器要跑在 5 台机器上。谁跑在哪台上？某台机器烧了，上面的容器谁来救？流量突然涨 3 倍，谁去加容器？

**底层逻辑**：人工回答这些问题太慢，所以 K8s 的核心思想是"**声明式管理**"——你不命令它怎么做，只**声明你要的最终状态**：
```
你说："web 服务要永远保持 3 个副本活着"
K8s：死一个 → 自动补一个；机器挂了 → 把上面的副本挪到活机器上
```
> [!note] 关键认知
> 这和管理一个道理：好的管理者不说"你每天几点几分做什么"，而是定好目标（3 个副本）和规则（健康标准），剩下让系统自己纠偏。**K8s = 一个永不睡觉、永不出错的值班运维**。滚动更新、自愈、扩缩容，全都是"声明目标 + 自动纠偏"这一个思想的不同应用。

### 3. Prometheus 监控 —— 从"用户骂了才知道"到"机器自己喊疼"

**朴素的问题**：没有监控时，故障的发现路径是：用户用不了 → 投诉 → 客服转给技术 → 技术开始查。**最宝贵的时间浪费在了"传递坏消息"上**。

**底层逻辑**：让每台机器**主动、持续地汇报自己的生命体征**（CPU、内存、磁盘……），中心存下这些时间序列数据，再配一套"**什么算不正常**"的判断规则：
```
机器每 15 秒上报指标 → 规则引擎比对阈值 → 异常持续 5 分钟 → 自动通知到人
```
> [!note] 关键认知
> 监控的本质是**把"排障"变成"看表"**。三个设计心法都有朴素道理：持续上报（体温要常测，不是病了才量）、持续一段时间才告警（打喷嚏不是肺炎，避免狼来了）、分级通知（发高烧打电话，小擦伤发消息就行）。

### 4. Ansible 自动化 —— 把"逐台登录操作"变成"一次批量执行"

**朴素的问题**：3 台服务器装软件，你 SSH 上去逐台敲同样的命令，第 3 台时已经开始走神敲错。300 台呢？

**底层逻辑**：既然每台机器要做的事**一模一样**，那就"**写一份剧本，所有机器照着演**"。Ansible 的两个核心设计：
```
无 agent：通过 SSH 直接远程执行，被管机器零安装（为什么这很重要？因为要装 agent 
          本身就得先逐台登录一遍——鸡生蛋问题）
幂等：  剧本跑 1 遍和跑 100 遍效果相同 → 你敢随时重跑，不怕搞乱
```
> [!note] 关键认知
> 类比：Shell 脚本是"**现场指挥**"（你必须人在场一步步喊），Ansible 剧本是"**施工图纸**"（写清楚要什么状态，工人自己核对现状，缺什么补什么）。幂等性就是图纸上写"房间里要有一盏灯"——已经有的房间工人不会砸墙重装。

## 🤖 AI 四件套：解决"模型很强但不会干活、不懂业务"

AI 工程的根本矛盾：**大模型有通用智能，但它不知道你的数据、不会调用你的工具、不懂你的行话**。四个项目恰好是四种"给模型补短板"的手段，层层递进：

### 5. RAG 知识库问答 —— 给模型配一个"开卷考试的资料室"

**朴素的问题**：问大模型"我们公司的报销流程"，它不知道——它的知识截止于训练那一刻，且从来不包含你的内部文档。但它**会读**——只要你把相关资料摆到它面前。

**底层逻辑**：**开卷考试**。不让模型背整间资料室（不可能也记不住），而是先按问题去资料室**检索**最相关的几页，摊在模型面前让它**看着资料回答**：
```
问题 → 去向量库查最相似的文档片段（检索）→ 片段+问题一起喂给模型（增强）→ 模型照资料作答（生成）
```
> [!note] 关键认知
> 向量检索的原理朴素得可爱：把每段文字变成一串数字（向量），意思相近的文字数字也接近——于是"查资料"变成了"算距离"。"报销流程"和"费用审批步骤"字面不同但向量很近，这就是语义搜索比关键词搜索聪明的原因。

### 6. 私有化 LLM 部署 —— 把"租来的大脑"换成"自己的大脑"

**朴素的问题**：调 OpenAI/DeepSeek 的 API，你的数据要发到别人的服务器上。金融、政务、医疗的数据**法律上就不允许出门**。

**底层逻辑**：开源模型（Qwen、DeepSeek）的**权重文件是公开下载的**——模型本质上就是一个几百 GB 的"超大参数文件 + 推理程序"。下载到自己服务器上跑，数据一步不出内网：
```
别人的 API：你的数据 → 翻山越岭 → 别人的 GPU → 结果回来（数据出门了）
私有化：   你的数据 → 你机房的 GPU（模型文件就住在里面）→ 结果（数据没动过）
```
> [!note] 关键认知
> 这个项目的工程难点不在"跑起来"（一条 docker 命令），而在**让 GPU 的显存装得下、算得快**——所以核心技术都是围绕显存的艺术：量化（参数从 2 字节压到 0.5 字节，模型"瘦身"）、KV Cache 管理（多用户对话历史怎么挤进显存，vLLM 的看家本领）、批处理（GPU 不能闲着，来一个算一个不如攒一批一起算）。

### 7. AI Agent —— 从"你问它答"到"你下任务它执行"

**朴素的问题**：聊天机器人只会"说"，不会"做"。你说"把上周销售数据整理成报表发群里"，它只能教你步骤，活还得你自己干。

**底层逻辑**：给模型装上"**手和脚**"（工具）和"**工作循环**"（闭环）：
```
模型不是一次说完答案，而是反复循环：
想（Reasoning）："我要完成报表，先得查数据"
做（Acting）：    调用查数据库的工具 → 拿到结果
再想：           "数据有了，该生成 Excel 了"
再做：           调用生成文件的工具……
直到任务完成才开口汇报
```
> [!note] 关键认知
> Agent = LLM（大脑）+ 工具（手脚）+ 循环（工作方法）。大脑决定**下一步做什么**，手脚负责**真去做**，循环保证**做砸了能根据结果调整再来**。工程上最重要的护栏也因此而来：查数据可以放手，发消息必须人确认——**自主权画在"不可逆操作"之前**。

### 8. LoRA 微调 —— 送模型去"岗前培训班"

**朴素的问题**：通用模型什么都会一点，但说起你们行业的"黑话"就露怯——医疗文书、法律条款、客服话术，语气、格式、术语全不对。

**底层逻辑**：模型的行为由参数决定，参数从训练中来。想让它学会新风格，就**拿行业范例再训练一轮**。但全量重训 70 亿参数要天价，LoRA 的巧思是：
```
不重训整个大脑，只在大脑的关键位置插几片"记忆贴片"（低秩矩阵）
原参数全部冻结 → 只训练贴片（0.3% 的参数）→ 消费级显卡也玩得起
学完：基座模型的通用能力还在，贴片注入了行业风格
```
> [!note] 关键认知
> **微调 vs RAG 的分工是面试必考题，也是理解两者的钥匙**：RAG 解决"知识问题"（不知道的事去查），微调解决"能力/风格问题"（知道但不会用行话说）。知识天天变用 RAG（改文档就行），风格长期稳定用微调（训一次管很久）。实际系统经常两个都用。

## 🧩 一张图看懂 8 个项目的关系

```
运维线（让系统跑起来、跑得稳）：
  Ansible(把机器配好) → CI/CD(把应用发上去) → K8s(让应用稳定跑) → Prometheus(盯着别出事)

AI 线（让模型懂业务、会干活）：
  私有化部署(有自己的大脑) → RAG(大脑接上知识库) → Agent(大脑学会用工具) → 微调(大脑学会行话)

交叉点：私有化 LLM 部署 是运维和 AI 的交叉技能，差异化最强
```
